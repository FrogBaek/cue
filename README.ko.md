# cue

**한국어** · [English](README.md)

AI 협업 개발을 위한 Claude Code 플러그인 모음입니다. 각 플러그인은 독립적으로
동작하고 프로젝트의 `.cue/` 아래 자기 디렉터리 하나만 사용합니다.

| 플러그인 | 하는 일 | 사용 디렉터리 | 상태 |
|---|---|---|---|
| `cue-dev` | 요구사항부터 병합까지의 개발 워크플로 | `.cue/dev/` | 0.1.0, 개발 중 |
| `cue-scan` | 프로젝트 분석 | `.cue/scan/` | 구상 |
| `cue-docs` | 프로젝트 현재 상태 문서화 | `.cue/docs/` | 구상 |

## 설치

```
/plugin marketplace add FrogBaek/cue
/plugin install cue-dev@cue
```

# cue-dev

## 해결하고자 하는 것

git 은 무엇이 언제 바뀌었는지는 남기지만 왜 그렇게 바꿨는지는 남기지 않습니다. 그
판단은 이미 닫힌 대화 안에 있습니다. 반년 뒤 코드를 열면 로직은 읽히는데 근거가
없습니다. 읽는 사람마다 다르게 추측하고, 리뷰어는 어떤 대안이 검토됐는지 모른 채
승인합니다.

이 부채는 이자가 붙습니다. 확인할 수 없는 결정 하나가 그 위에 쌓이는 다음 결정까지
어렵게 만들기 때문입니다. AI 와 함께 일하면 속도가 붙는 만큼 더 빨리 쌓입니다.

cue-dev 가 이 비용을 없애주지는 않습니다. 대신 코드를 읽을 때가 아니라 설계할 때
치르게 하고, 더 불어나지 않게 잡아둡니다. 요구사항·설계·버린 대안·결과를 작업 중에
기록해 코드 옆에 커밋하므로 나중에 어느 줄에서든 되짚어갈 수 있습니다.

```
git blame → 커밋 → KEY → .cue/dev/<KEY>/design.md
```

## 핵심

- **기록이 코드와 같이 다닙니다.** 같은 브랜치의 `.cue/dev/<KEY>/` 에 커밋되므로 PR
  이 diff 와 판단 근거를 함께 나릅니다.
- **단계마다 멈추고 확인받습니다.** 자동으로 다음 단계로 넘어가지 않습니다.
- **진행 상태를 세션이 아니라 git 에서 읽습니다.** 커밋 마커로 판정하므로 오늘 시작한
  작업을 다음 주에, 다른 세션에서, 다른 모델이 이어받을 수 있습니다.
- **사실 확인은 스크립트가 합니다.** 어느 단계까지 갔는지, 되돌리면 무엇을 잃는지,
  백업으로 복구할 수 있는지 전부 테스트가 붙은 스크립트가 답합니다.

## 사용법

### 저장소당 한 번

```
/cue-dev:init
```

커밋 마커 접두사, 기록 언어, 리모트 이름, `.cue/dev/` 를 커밋할지를 정합니다.
물어보고 확인받은 뒤에 `.gitignore` 와 설정 파일을 씁니다. 다시 실행해도 안전합니다.

### 작업 시작

```
/cue-dev:start 로그인 실패 시 5회 제한 추가
```

하려는 일을 그냥 문장으로 쓰면 됩니다. 아무것도 주지 않으면 물어봅니다. 이 단계에서
KEY 를 제안받고 확인하면 작업 공간과 `demand.md` 가 생깁니다.

`/cue-dev:start` 는 넘겨준 요구사항을 그대로 받습니다. 쓰는 에이전트에 이슈 트래커
MCP 가 붙어 있다면 그 텍스트가 트래커에서 읽어 온 티켓 본문이어도 됩니다. 티켓을
식별하는 값만 넘기고 본문은 에이전트가 찾아오게 하면 됩니다.

```
/cue-dev:start PROJ-142
```

그 값이 그대로 KEY 가 되므로 KEY 를 다시 제안하지 않습니다. 형식을 검증하지는
않지만 디렉터리 이름과 브랜치 이름으로 쓰이므로, 맨숫자보다 `PROJ-142` 쪽이
낫습니다. 그 텍스트가 도구에서 왔는지 붙여넣은 것인지 대화에서 나온 것인지는 어느
쪽이든 `demand.md` 에 남습니다.

KEY 는 이후 모든 명령이 이 작업을 찾는 이름입니다. 브랜치에 기록되므로 **다음부터는
KEY 를 넘길 필요가 없습니다.**

### 단계별 진행

```
/cue-dev:design      요구사항을 파고들어 design.md 를 씁니다
/cue-dev:plan        설계를 독립적인 태스크로 나눠 plan.md 에 적습니다
/cue-dev:implement   태스크 단위로 구현하고 결과를 기록합니다
/cue-dev:finish      기록을 검증하고 통합한 뒤 outcome.md 를 씁니다
```

인자 없이 순서대로 실행하면 됩니다. 각 명령은 만든 결과를 보여주고 멈춥니다. 검토하고
나서 다음 명령을 실행하면 그때 넘어갑니다. 마음에 들지 않으면 그 자리에서 고쳐달라고
하면 됩니다.

`design` 은 요구사항이 모호하면 되묻고 버린 대안까지 기록에 남깁니다. `plan` 은
태스크 간 의존 관계를 그래프로 그려 붙입니다. `implement` 는 태스크마다 커밋을 남기고
`outcome.md` 의 해당 행을 채웁니다. `finish` 는 기록이 빠짐없이 채워졌는지 검증한 뒤
base 브랜치로 병합하거나 브랜치를 그대로 둡니다.

### 지금 어디까지 왔는지

```
/cue-dev:status
```

어느 단계까지 갔고 다음이 무엇인지, 되돌린다면 무엇을 잃는지 보여줍니다. 며칠 쉬었다
돌아왔거나 세션이 바뀌었을 때 여기부터 시작하면 됩니다. 다른 브랜치에 서 있다면
`/cue-dev:status PROJ-142` 처럼 KEY 를 넘깁니다.

### 잘못 갔을 때 되돌리기

```
/cue-dev:redo plan
```

그 단계와 그 뒤에 한 것을 전부 되돌립니다. 되돌리기 전에 현재 상태를 백업 브랜치로
저장하고, 무엇이 버려지는지 보여준 뒤 확인을 받습니다.

되돌린 것을 다시 되돌릴 수도 있습니다. 전용 인자가 있는 것이 아니라 그냥 말하면
됩니다.

```
/cue-dev:redo   →  "방금 되돌린 거 취소하고 백업으로 돌아가줘"
```

그러면 그 작업의 백업이 전부 나열됩니다. 각각 어느 단계를 담고 있는지, 커밋이 몇 개
돌아오고 몇 개가 버려지는지까지 같이 나옵니다. 어느 것으로 갈지는 직접 골라야 합니다.
복구 직전 상태도 백업되므로 복구 자체를 다시 되돌릴 수 있습니다.

### 명령 정리

`<>` 는 필수, `[]` 는 선택입니다. `[KEY]` 는 생략하면 현재 브랜치에서 찾습니다.

| 명령 | 인자 |
|---|---|
| `/cue-dev:init` | 없음 |
| `/cue-dev:start` | `[요구사항 또는 티켓 본문] [KEY]` |
| `/cue-dev:design` | 없음 |
| `/cue-dev:plan` | 없음 |
| `/cue-dev:implement` | 없음 |
| `/cue-dev:finish` | 없음 |
| `/cue-dev:status` | `[KEY]` |
| `/cue-dev:redo` | `<demand\|design\|plan\|implement> [KEY]` |

## 기록을 팀과 공유할지

`.cue/dev/<KEY>/` 에 쌓이는 기록을 저장소에 커밋할지 로컬에만 둘지는
`/cue-dev:init` 에서 고릅니다. 고른 대로 `.gitignore` 규칙이 들어갑니다.

- **커밋합니다.** 팀원이 PR 에서 diff 와 함께 요구사항·설계·결과를 봅니다. cue-dev 가
  기본으로 삼는 쪽입니다.
- **커밋하지 않습니다.** `.cue/dev/` 를 통째로 무시합니다. 설계 문서를 다른 시스템에서
  관리하거나 저장소에 파일을 추가하기 곤란할 때 씁니다.

어느 쪽이든 워크플로는 똑같고 팀에 보이는지만 달라집니다. 구현 중 쓰는 스크래치
(`.cue/dev/sdd/`)와 워크트리 디렉터리는 항상 무시됩니다.

## 하지 않는 일

- **이슈 트래커 노릇.** 지라나 깃허브 이슈를 대체하지 않습니다. 쓰는 트래커가 있으면
  해당 MCP 를 따로 붙이고, 없으면 `/cue-dev:start` 가 직접 물어봅니다.
- **코드 리뷰.** 리뷰받을 수 있는 상태까지만 만듭니다. 리뷰는 사람이 합니다.
- **프로젝트 문서 관리.** 읽지도 고치지도 않습니다.

## 기여하기

체크아웃에서 바로 돌리려면 다음과 같이 실행합니다.

```bash
claude --plugin-dir /path/to/cue
tools/run-tests.sh          # 32개 스위트, 약 6분
```

나머지는 [CONTRIBUTING.md](CONTRIBUTING.md) 에 있고, 각 스위트가 무엇을 잡는지는
[docs/testing.md](docs/testing.md) 에 적어뒀습니다.

**저장소 안은 전부 영어로 씁니다.** 커밋 메시지, 이슈, PR, 코드 주석, `docs/` 까지
해당합니다. 예외는 README 하나이고 언어별 번역본을 둡니다.

변경 내역은 [CHANGELOG.md](CHANGELOG.md) 에 있습니다.
